# WN 0026 - Model Parameters (Givens)

- **Status**: *Draft*
- **Discussions-To:** TBD
- **Author:** Michael Toy
- **Experiment-ID:** *givens*

## A note on the name

This started life as **model parameters** and that is what they still are: values declared in a model and supplied at run time. During the design process the name shifted to **givens** — partly because Malloy already uses "parameters" for source/query parameters, and partly because "given" reads naturally at every site (`given: TENANT :: string`, `$TENANT`, `runtime.givens`). The mechanics described below are stable; the spelling is still provisional and may change before the feature ships.

## Motivation

Users want to parameterize Malloy models with values supplied at run time. A primary expected use is **row-level access control** — writing a model once where sources carry filters like `where: x.tenant_id = $TENANT`, and supplying the tenant value per API call.

Other use cases: configuration values (max row limits, date cutoffs), session context (user role, locale), and any situation where one compiled model should be reusable across multiple invocations with varying context.

Stipulating these values at the model level composes better than parameterizing at the source level. A model can apply filters globally and each source implements them as appropriate, without per-source plumbing.

## Declaration

A new top-level statement `given:` introduces givens to a model:

```malloy
given:
  TENANT :: string
  MAX_ROWS :: number is 1000
  CUTOFF_DATE :: date is @2024-01-01
```

A given declaration has a name, a type, and an optional default. The default is an expression that may include constants and references to other givens.

Type is any Malloy atomic type, including compound types and `filter<T>`:

```malloy
given:
  ROLE :: string
  ALLOWED_ROLES :: string[]
  SESSION :: { user_id :: string, tenant :: string }
  TENANT_FILTER :: filter<string>
```

Annotations work the same as on sources, queries, and other named declarations:

```malloy
given:
  # label="Order Status" possible_values=[COMPLETE, CANCELLED]
  ORDER_STATUS :: string is "COMPLETE"
```

These annotations surface through the introspection API (see *API: introspection*) so frontends can render given-input UI without manual wiring.

## Reference

Inside any expression, a given is referenced with a leading `$`:

```malloy
source: orders_for_user is orders extend {
  where: orders.tenant_id = $TENANT
}

query: recent_orders is orders_for_user -> {
  where: order_date >= $CUTOFF_DATE
  limit: $MAX_ROWS
}
```

The `$` sigil marks a reference as coming from the given namespace rather than the source/view/field namespace. Given names share the declaration namespace with other top-level names, so `source: x is ...` combined with `given: x :: string` is a declaration-time conflict error.

`$` appears *only* at expression references. Declarations, imports, and supply sites use the bare name — there is no naming ambiguity to resolve in those positions.

## Scope and Namespaces

Each model has a flat **given namespace** — the names its caller sees. All givens declared in a file are visible to every source, view, query, and expression in that file.

Givens behave like every other top-level named thing under import:

- **Non-selective.** `import "b.malloy"` brings B's full export surface into A: sources, queries, views, *and* givens, all under their original names.
- **Selective.** `import { source1 } from "b.malloy"` brings in only what's listed. Givens not in the list are not surfaced. To surface a given, list it: `import { source1, MAX } from "b.malloy"`.
- **Rename.** Uses the existing `LOCAL is REMOTE` grammar: `import { B_MAX is MAX_SIZE } from "b.malloy"`.

An imported source can reference a given that the importer didn't surface. The reference still works internally — what surfacing controls is *who can supply a value*. A surfaced given is in the importer's namespace and the caller can supply it; an unsurfaced given relies on its declaration-site default.

Name collisions are compile-time errors. Disambiguate with rename-on-import:

```malloy
import { source1, B_MAX is MAX_SIZE } from "b.malloy"
import { source2, C_MAX is MAX_SIZE } from "c.malloy"
```

### Suggested convention: shared project-level givens

A multi-tenant project where many models reference `$TENANT`, `$USER_ROLE`, `$REGION` typically wants those declared once and shared. The recommended convention: put them in their own `.malloy` file and bare-import it at the top of every root file:

```malloy
// tenant_givens.malloy
given:
  TENANT :: string
  USER_ROLE :: string is "viewer"
  REGION :: string is "us-east-1"
```

```malloy
// orders.malloy — and every other root file in the project
import "tenant_givens.malloy"

source: orders is duckdb.table('warehouse.orders') extend {
  where: tenant_id = $TENANT and region = $REGION
}
```

This is convention, not language enforcement.

## Satisfiability

A query referencing `$X` is **satisfiable** if either:
- `$X` is in this model's namespace (the caller can supply a value at run time), OR
- `$X` has a default at its declaration site.

A query is **unsatisfiable** if neither — there is no path for the value to ever arrive. The translator catches what it can at translation time; the rest fail at run time with a missing-given error.

Latent definitions (views/dimensions/measures that reference `$X` but are never invoked) don't need to be satisfiable. Satisfiability is a property of running queries, not of the namespace at large.

## API: supplying values

Givens can be supplied at three layers, merged per-key:

1. **Declaration-site default** — `given: X :: T is value`.
2. **Per-runtime** — applied to every query that runs through a runtime. Supplied either via a JSON file pointed to by config (`givensPath`) or directly on the `Runtime` constructor.
3. **Per-query** — supplied on a single `.run({ givens: ... })` call. Overrides the runtime layer for that call.

### Per-runtime supply via `givensPath`

A project's `malloy-config.json` can point at a JSON values file:

```jsonc
// malloy-config.json
{
  "givensPath": "./local-givens.json"
}
```

`givensPath` accepts the same `{ "env": "VAR_NAME" }` form as other string-valued config properties, so dev / prod / CI can share one project config and differ only in env binding.

The values file is plain JSON, keyed by caller-facing surface names:

```jsonc
{
  "TENANT": "acme",
  "USER_ROLE": "admin",
  "CUTOFF_DATE": "2024-01-01"
}
```

### Per-runtime supply via the constructor

When the host has values in hand (multi-tenant servers, tests, scripts), they can be passed directly:

```typescript
const runtime = new Runtime({
  config,
  givens: { TENANT: claims.tenant_id, USER_ROLE: claims.role },
  urlReader,
});
```

Constructor-supplied values **merge over** the file at `givensPath` per-key — the constructor wins on overlap; other keys fall through. A project config with sane defaults plus a request handler supplying only the JWT-derived `TENANT` works without read-merge-write in the host.

### Per-query overrides

```typescript
await query.run({
  givens: {
    STATE_FILTER: "CA",
    LIMIT_OVERRIDE: 50,
  }
})
```

Available on every compile-or-run entry point: `runtime.loadQuery(...).run(options)`, `preparedQuery.getPreparedResult(options)`, `preparedQuery.getSQL(options)`.

### Where each kind of value lives

| What you have | Where it goes |
|---|---|
| Default for when no caller supplies a value | `given: X :: T is value` |
| Static value shared across the team, in git | JSON file at `givensPath` |
| Environment-specific value (dev / prod / CI vary) | JSON file at `givensPath`, with the path resolved via `{ "env": "VAR_NAME" }` |
| Value the host has in hand in JS (request claims, test setup) | Runtime constructor: `new Runtime({ givens: { ... } })` |
| Per-call override (UI dropdown, dashboard parameter) | `query.run({ givens: { ... } })` |

### Finalizing givens at the runtime

A multi-tenant deployment needs to declare that some givens — `TENANT`, `USER_ROLE`, `REGION` — are bound by the runtime and **cannot** be overridden per-query. Without this guarantee, a downstream endpoint that accidentally accepts user-controlled query params and plumbs them into `.run({ givens: ... })` is a tenant-leak vulnerability. Finalize is a security primitive at the API surface.

```jsonc
{
  "givensPath": { "env": "GAME_STORE_GIVENS" },
  "finalizeGivens": ["TENANT", "USER_ROLE", "REGION"]
}
```

A `.run({ givens: { TENANT: ... } })` for a finalized name throws at API entry, before any IO. Finalized names are also filtered out of `Model.givens` and `PreparedQuery.givens`, so UIs prompting for per-query inputs don't render editors for them.

### Accepted JS shapes

Both the JSON values file and per-query `givens` maps speak the same per-type shapes:

| Malloy type | JS |
|---|---|
| `string` | JS string |
| `number` | `number`, `bigint`, or string (for big integers / DECIMAL) |
| `boolean` | JS boolean |
| `date` | ISO date string `"2024-01-15"` |
| `timestamp` (naive) | ISO string without offset |
| `timestamptz` | JS `Date` or ISO string with offset |
| `T[]` | JS array; each element validated against `T` |
| `{ name :: T, ... }` | JS object; values validated recursively |
| `filter<T>` | JS string (Malloy filter expression source) |

Nulls are legal anywhere. Compound types are supported end-to-end with type errors that point at the offending path (`givens.SESSION.user_id: expected string, got number`).

## API: introspection

```typescript
class Model {
  get givens(): ReadonlyMap<string, Given>;
}

class PreparedQuery {
  get givens(): ReadonlyMap<string, Given>;  // subset this query references
}
```

`Model.givens` returns every supplyable given the model surfaces (drives whole-model parameter-editor UIs). `PreparedQuery.givens` returns the subset *this query* references (drives "run this query" forms that prompt only for relevant givens).

Each entry exposes `name`, `id`, `type`, `default`, `location`, and the standard `tagParse` / `getTaglines` annotation accessors.

Finalized names are filtered from both maps.

## Relationship to source parameters

Givens and source/query parameters (`source: foo(x :: string) is ...`) are **complementary, not replacement**. They serve different scopes:

| | Givens | Source/query parameters |
|---|---|---|
| Scope | Model-wide, one namespace | Per-instantiation |
| Multiplicity | One value per ID per compilation | Many simultaneous bindings |
| Use case | Configuration, RLAC, packaging | Currying, multiple versions of the same source side-by-side |
| Binding location | Per-runtime (config or constructor) with per-query overrides | Call site at instantiation |

Givens fit "I want one value visible everywhere in this compilation." Source parameters fit "I want two differently-bound copies of the same thing in this compilation." The original WN-0026 draft anticipated subsuming source parameters; the design landed on keeping both.

## Experimental Status

Givens ship as experimental, behind the `experimental.givens` compiler flag. The design is untested against real workloads and may need revision based on what we learn.

## Comparison with WN-0002

Lloyd's [WN-0002](../WN-0002-parameters/wn-0002.md) proposed a broader parameter feature bundling several capabilities. This proposal addresses some directly, leaves some out of scope, and picks up others as a natural consequence of the model-level design.

| Capability | WN-0002 | WN-0026 (givens) |
|---|---|---|
| Binding scope | Per-source / per-view / per-dimension / per-measure | Model-wide (one namespace per compilation) |
| Binding timing | At invocation site (`orders(x='foo')`) | Per-runtime (config or constructor) with per-query overrides |
| Constant parameters (string, number, date) | Yes | Yes — any Malloy atomic type, including compound types |
| Default values | Yes | Yes — including expressions over other givens (default chains) |
| Parameterized views | Yes, via per-view parameter slots | Yes — a view referencing `$PARAM` in its body is parameterized |
| Annotations for UI hinting | Yes | Yes — uses standard annotation system; introspection API exposes metadata |
| Composes across imports | Not discussed | Yes — namespace rules with rename-on-import; non-selective imports auto-surface |
| RLAC / row-level access control | Possible but awkward | Direct fit — model-wide binding, with `finalizeGivens` as security primitive |
| `filter<T>` as a parameter type | Yes, central | **Yes** — supported; bound JS string parsed and type-checked at SQL emission |
| Filter helper functions (`begin_date`, etc.) | Yes | Not in scope — paired with future filter-type work |
| Abstract functions (sources / views as invocable) | Yes | Not in scope — orthogonal feature, would need its own WN |
| "Bypass default" semantics (ALL / empty string) | Yes | N/A — callers supply any value, including ones that neutralize a default |

## Deferred work

These are recognized but not in MVP:

- **Source-level `final` import modifier** — freezing imported givens at the import boundary so downstream callers can't override them. Designed but deferred until named namespaces and explicit exports land; under flat namespaces, the multi-import-conflict case has no clean resolution.
- **Table-name givens** — `given: TBL :: table` and `source: orders is duckdb.table($TBL)`. Today's answer is the existing `virtualTables` mechanism; whether a `::table` given type is meaningful or `virtualTables` is the durable answer is an open design question.
- **Stable wire API for givens** — separate workstream, tracked at malloydata/malloy#2784.
- **Naming** — as noted up top, `given` is provisional.
